# StudentMessageSharePRO · Linux 部署改造文档

> 版本：v1.0（2026-11-09）
> 范围：仅分析代码与给出改造方案，**本次未修改任何代码**。
> 结论口径：能否同时兼容 Windows 与 Linux 双系统运行。

---

## 0. 结论摘要

### 0.1 总体判断

**可以做到一套代码同时跑 Windows 与 Linux**，但需要新增一个 Linux 启动入口、把 Windows 专属能力（托盘、命名互斥体、DLL 读卡）做平台隔离，并把“数据目录/配置目录”从代码目录中分离出来。核心业务代码（学生、出勤、保险、毕业、档案、区划、模板导出、备份）本身跨平台度很高。

| 维度 | 结论 |
|---|---|
| Web 框架与业务代码 | ✅ 已跨平台（Flask + SQLite + openpyxl + python-docx + qrcode + 纯 Python 拼音字典） |
| 静态资源 | ✅ 已全部本地化到 `static/vendor/`，无外网 CDN 依赖 |
| 启动入口 | ❌ Windows 托盘入口 `run_with_tray.py` 在 Linux 上**必然启动失败** |
| 身份证读卡（服务端 DLL） | ❌ Linux 不可用（必须降级为浏览器 WebSocket 通道） |
| 配置/数据目录 | ⚠️ 默认落在代码目录，只读部署会启动失败，必须设置 `USER_DATA_DIR` |
| 进程模型 | ⚠️ 应用含大量**进程内内存状态**，Linux 生产环境只能单进程多线程运行 |
| 时区/字体/文件名大小写 | ⚠️ 需按清单核对，否则会出现日期、照片、导出字体等“软故障” |

### 0.2 必须改造的 P0 项（3 类）

1. **新增 Linux 无头启动入口，并与 Windows 托盘入口并存（已决策）**：`run_with_tray.py` 在导入阶段就调用 `ctypes.windll`（[run_with_tray.py:89-92](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/run_with_tray.py#L89-L92)、[run_with_tray.py:109](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/run_with_tray.py#L109)），Linux 上直接 `AttributeError` 退出。两个入口独立存在、互不 import，不做统一 `main.py` 分流（见 §3.2）。
2. **数据目录与代码目录分离**：`config.py` 默认把 DB/日志/照片/上传全部放在代码目录（[config.py:10](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/config.py#L10)），且端口配置文件 `config.txt` 也写在代码目录（[config.py:13](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/config.py#L13)、[config.py:42-50](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/config.py#L42-L50)），只读部署会直接抛 `RuntimeError`。
3. **生产运行方式**：不能用 `python app.py`（开发服务器）+ 不能多 worker（内存态进度字典、备份单例、登录限流），需由 `run_server.py`（内部 waitress）或 `gunicorn -w 1 --threads N` + systemd 托管。

### 0.3 功能降级 1 项（不阻塞部署）

- **服务端读卡 API** `/api/read_id_card` 依赖 `ctypes.WinDLL` + `sdk/*.dll`（[services/card_reader.py:51](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/services/card_reader.py#L51)），Linux 不可用。
- 但前端主通道是**浏览器侧 WebSocket**（`ws://127.0.0.1:9001`，[card_reader.js:11](file:///c:/Users/Administrator/Documents/Trae-CN/StudentMessageSharePRO-v2/static/js/card_reader.js#L11)），即“Linux 服务器 + Windows 操作员电脑装华视监控软件”的组合**仍然可用**；只有“读卡器 USB 直插服务器”的场景会失效。

## 3. 逐项改造方案（建议代码，本次未实施）

### 3.1 P0：Linux 启动入口

新建 `run_server.py`（与 `run_with_tray.py` 并列，Windows 入口保持不动）：

```python
import os
import sys
import logging
import logging.handlers
import signal
import threading
import time

BASE_DIR = os.path.abspath(os.path.dirname(__file__))
# 关键：Linux 下数据目录必须独立于代码目录
os.environ.setdefault('USER_DATA_DIR', os.environ.get('USER_DATA_DIR', BASE_DIR))
DATA_DIR = os.environ['USER_DATA_DIR']

for sub in ('data', 'uploads', 'logs', 'databackup', 'static/photos'):
    os.makedirs(os.path.join(DATA_DIR, sub), exist_ok=True)

# 日志初始化必须在导入 config/app 之前（与 run_with_tray.setup_logging 等价）
...

def main():
    from waitress import serve          # 或 gunicorn 由命令行启动
    from app import app
    host = os.environ.get('STUDENT_HOST', '0.0.0.0')
    from config import PORT
    serve(app, host=host, port=PORT, threads=int(os.environ.get('WEB_THREADS', '8')))

if __name__ == '__main__':
    main()
```

要点：

1. **不要 import `run_with_tray`**（会被 `ctypes.windll` 打死）。
2. 保持 `USER_DATA_DIR` 在导入 `config` 前设置（`config.py:10` 是模块级读取）。
3. 日志路径写成 `DATA_DIR/logs/app.log`，避免代码目录只读。
4. 收到 `SIGTERM` 时无需调用 `/shutdown`，进程退出即可；SQLite WAL 具备崩溃恢复能力，若要优雅收尾可显式 `PRAGMA wal_checkpoint(TRUNCATE)`。

### 3.2 P0：双入口并存（已决策）

> **决策（2026-11-09）：采用“两个入口并存”，不新增统一 `main.py`，也不做 `os.name` 平台分流。**

理由：

- 托盘 / Tk 弹窗 / 命名互斥体只属于 Windows 桌面场景，不应进入 Linux 依赖图；
- Linux 由 systemd 直接调用启动命令，避免多一层无意义的转发脚本；
- 故障边界清晰：两个入口互不依赖，Windows 入口的改动不会影响 Linux 部署，反之亦然。

入口职责矩阵：

| 入口 | 平台 | 启动方式 | 职责 |
|---|---|---|---|
| `run_with_tray.py`（现有） | Windows | 双击 EXE / 桌面快捷方式 | 单实例互斥、托盘菜单、启动完成弹窗、后台线程运行 Flask |
| `run_server.py`（新增） | Linux | systemd / 容器 / 手动 | 无头启动、日志初始化、数据目录初始化、waitress 或 gunicorn |

启动方式：

```bash
# Windows（现有方式，完全保持不变）
run_with_tray.exe                       # 或 python run_with_tray.py

# Linux（开发调试）
USER_DATA_DIR=/var/lib/student-message-share python run_server.py

# Linux（生产，systemd 直接拉起 WSGI，见 §5.4）
systemctl start student-message-share
```

约束：

1. 两个入口**各自独立初始化**，不互相 import；Linux 入口绝不能 import `run_with_tray`（会被 `ctypes.windll` 打死）。
2. 目录/日志初始化逻辑允许在两端各有一份小段重复代码；如后续确有需要再抽 `bootstrap.py`（非本期必需）。
3. Linux 入口只负责“无头启动”，不提供任何托盘/弹窗能力；Windows 入口不感知 Linux 部署方式。

- 迁移旧数据：把 Windows 的 `user_data/` 整体拷到 `/var/lib/student-message-share`，保持 `data/`、`static/photos/` 层级不变；`secret.key` 一并拷贝可保持登录态与已分发链接有效。

### 3.12 P2：HTTPS / 反向代理（可选）

- 若前置 nginx TLS：`SESSION_COOKIE_SECURE=1`，并给 Flask 加 `ProxyFix`（当前未配置，`url_for`/重定向会按 http 生成；功能可用但不优雅）。

## 4. 双系统兼容方案（两种落地路线）

### 路线 A（已采纳，最小改动）

- 核心代码**不动**（唯一建议动的是 `card_reader.py` 的平台守卫）。

- Linux：新增 `run_server.py` + systemd。

- 差异只体现在**入口脚本与部署配置**，业务代码 100% 共享。

优点：风险最低，回归面最小，符合当前“桌面端为主”的产品形态。
缺点：`run_with_tray.py` 与 `run_server.py` 有少量重复初始化（日志、目录），可后续抽公共 `bootstrap.py`。

### 路线 B（平台适配层，长期更干净）

```
core/                      # 现有业务（不变）

├── single_instance.py     # Windows CreateMutexW / POSIX flock
├── notify.py              # 托盘+弹窗 / 纯日志

└── server.py              # app.run / waitress / gunicorn 适配

run_server.py              # Linux 入口
```

适合后续要出 Linux 发行版、或要做容器化时再引入。当前阶段不建议一次性做大改，避免引入回归。
